Added out-of-order session vouchers inside a reorder window. A server opts in with `SessionMethod::with_reorder_window` (`DEFAULT_REORDER_WINDOW` is 30 seconds, and windows are capped at `MAX_REORDER_WINDOW_SECS`, one day; clients treat a longer advertised window as none) and advertises `reorderWindow` in its session challenges. It then accepts each voucher increment `(after, cumulativeAmount]` once, also below the highest accepted voucher, as long as it is newer than the window, and refuses stale and replayed vouchers as `delta-too-small` without naming the channel's accepted amount. Requests are still charged from the highest voucher. A client paying such a server allocates each voucher from the channel's counter (atomically in the channel store, with one `UPDATE ... RETURNING` for `SqliteChannelStore`) and sends it with `after`, each range covering the challenge's `minVoucherDelta`, so concurrent requests, and processes sharing a store, pay over one channel without waiting for each other. A `minVoucherDelta` above `max_amount` or `max_atomic_amount` refuses the challenge, since each voucher would sign at least that much for one request. A range refused as already accepted or stale is never covered again, however many refusals overlap. Every voucher such a client signs, also on the serialized path (after waiting for the payment lock or a top-up, and on legacy channels), carries `after`; a `payment-need-voucher` that no new range can reach within the deposit is refused instead of signed without it. Receipts for these payments cost each request its quoted amount, since concurrent receipts arrive in any order, and the channel's recorded `spent` only rises. It moves its counter up to a server's accepted amount only when the session snapshot carries a voucher this channel's signer signed for it; bare amounts in receipts and refusals never raise it. With a reorder window, a voucher whose write loses a compare-and-swap on a store shared by several server instances is applied again to the fresh state, up to eight times. A serialized payment whose top-up others use first tops up again for its own voucher, up to three times. A prepaid voucher is only allocated on the channel its cached spent amount describes. MCP clients report a refused credential to the provider before rolling it back, as the HTTP flow does. Without `reorderWindow` nothing changes. Session voucher payloads gained the optional `after` field, `TempoSessionMethodDetails` gained `reorder_window`, `ChannelState` gained `window`, `ErrorCode` gained `ConcurrentUpdate` (returned by `ChannelStoreAdapter` for a lost compare-and-swap, previously `Internal`), the client `ChannelStore` gained `allocate` and `allocates_atomically` (it raises the counter to an absolute target or by an amount, whichever is higher, in one atomic step; only stores that override both, such as the memory and SQLite stores, are allocated from concurrently; others pay serialized), and `PaymentProvider` gained `observe_refusal`.
